# 实施与维护计划

本计划保留产品阶段地图和后续维护边界。源码、[产品设计](../DESIGN.md)、[架构与合约](ARCHITECTURE_AND_CONTRACTS.md)以及[验收手册](ACCEPTANCE_AND_LIVE_RUNBOOK.md)是具体实现和验收依据。阶段名称不是当前源码自动通过的证明，实际结果见[验证状态](release-evidence.md)。

| 阶段 | 工作范围 | 验证边界 |
| --- | --- | --- |
| M00 | 能力与执行环境核查 | 固定实际客户端、接口、权限和未知项；探针不代替产品闭环 |
| M01 | 核心身份、授权和持久化 | 所有入口经过统一 handler；记录隔离与失败恢复 |
| M02 | 仓库证据和代码基线 | 固定快照、授权范围、排除项和引用；不把工作区当成自动一致 |
| M03 | 多轮会话和人工接管 | 明确会话身份、恢复及未知发送；模拟不能替代本人操作 |
| M04 | 受限代码调查 | 明确授权、路径、预算及隔离；调查与源码实施分离 |
| M05 | 完整成果交付与本地决策 | 验证版本、文件集、原件和 route；区分接收、审查、采纳、实施 |
| M06 | 双入口产品化与安装 | 验证实际包、安装、配置、升级、备份和恢复 |
| M07 | 并发、故障、安全与中立性 | 覆盖跨项目、撤权、重放、崩溃及适用第二运行时条件 |
| M08 | 真实验收与最终交付 | 用同一声明版本关联适用证据；未完成项保持未通过 |

当前优先 Codex 与 ChatGPT 的个人使用路径。第二运行时和完整中立性验收后置；这一优先级不改变完整 `release_ready` 条件。历史失败、跳过及未知结果保留，不因整理文档或某一阶段完成而改写。

## 有界批次与验证

按 D237，将影响同一验收场景或安装路径的已知问题集中成有界候选批次：保留各项复现和必要诊断，完成相关修复后去重执行受影响检查，再按实际需要打包、安装或进行真实验证。已有通过范围未变化时，不因记账或每个小修复重复整套验证；文档和回执变更本身不触发重装。

安全和权限、跨项目边界、实际受影响接口，以及最终统一版本发布所需测试不能由批处理省略。新增机制应对应具体失败或验收缺口，并有可观察退出条件；可选诊断不应自动变成发布前置。验证成本按项目和用户的当前限制控制。

需要真实账号、人工接管或其他人类操作时，记录准确状态和范围；不能把离线、模拟、用户报告或不同版本证据合并标为统一 LIVE 通过。完整发布仍需满足验收手册中的离线、旗舰真实路径、安装恢复、第二运行时及其他适用关卡。
